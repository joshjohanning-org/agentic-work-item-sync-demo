# Jira and GitHub agentic work-item sync demo

This public repository demonstrates a label-triggered, agentic workflow that connects Jira Cloud work items to GitHub Issues and GitHub Projects.

The design treats **Jira as the system of record by default** and **GitHub as the workspace where developers plan and deliver the work**. Developers can explicitly push selected GitHub fields back to Jira when GitHub has the intended value.

This is a functional reference implementation for a future Digital.ai Agility integration. It does not connect to Digital.ai Agility.

## What the demo proves

- A scheduled agent can discover new Jira work and create linked GitHub issues.
- A developer can pull current Jira values into GitHub with a label.
- A developer can explicitly push current GitHub values into Jira with a different label.
- One agentic workflow handles both on-demand directions.
- Jira-owned source content can refresh without replacing GitHub-owned implementation notes.
- GitHub App authentication can update organization Project fields.
- Copilot inference uses the repository `github.token` billing path and `model: auto`.

## Architecture

```text
                      every 6 hours or manual run
Jira GHAW project ───────────────────────────────────▶ GitHub Issues
      ▲                                                    │
      │                                                    │ added to
      │                                                    ▼
      │                                              GitHub Project 26
      │                                                    │
      │            sync-to-jira                            │
      └────────────────────────────────────────────────────┘

Jira GHAW issue ───────────── sync-from-jira ─────────────▶ GitHub issue + Project fields
```

There are two agentic workflows:

| Workflow | Trigger | Purpose |
|---|---|---|
| [Import New Jira Issues](.github/workflows/jira-import-new.md) | Every six hours or manual dispatch | Create GitHub issues for Jira items that do not have one, then refresh mapped fields on existing items |
| [Sync Jira and GitHub Work Item](.github/workflows/jira-sync-on-command.md) | `sync-from-jira` or `sync-to-jira` label | Synchronize one linked item in the direction explicitly selected by the developer |

The compiled `.lock.yml` files are generated by `gh aw compile`. Edit the Markdown source files, not the lock files.

## Why the direction is explicit

GitHub Projects exposes an `updatedAt` timestamp for a whole Project item, not a trustworthy edit timestamp for every field. Jira also exposes an issue-level updated timestamp. A simple "last edited wins" rule cannot determine which individual value changed and would let the synchronization itself create newer timestamps. That can cause silent overwrites or ping-pong updates.

This demo uses two one-shot command labels instead:

| Label | Winner | Behavior |
|---|---|---|
| `sync-from-jira` | Jira | Pull Jira-owned work-item values into the GitHub issue and Project |
| `sync-to-jira` | GitHub | Push mapped GitHub issue and Project values into Jira |

Both labels are handled by the same workflow. If both labels are present, the workflow makes no field changes, posts a conflict comment, and removes both command labels.

This is deliberate conflict resolution: the person applying the label chooses which side wins. It is easier to explain and safer to demonstrate than pretending coarse timestamps provide field-level conflict detection.

## Scheduled import

`.github/workflows/jira-import-new.md` runs every six hours and supports manual dispatch.

It:

1. Reads the ten most recently created issues in Jira project `GHAW`.
2. Searches this repository for an existing issue containing each Jira key.
3. Creates up to three missing GitHub issues per run.
4. Adds the `jira-synced` label.
5. Creates a workflow-managed `## Jira source` section.
6. Creates a separate `## Developer notes` section.
7. Refreshes Priority, Effort, and Project fields for Jira items that already exist in GitHub.

The importer deduplicates by Jira key and title. Newly created issues receive Project values on the next scheduled or manually dispatched importer run.

## On-demand synchronization

### Pull Jira into GitHub

Apply `sync-from-jira` to a linked GitHub issue.

The workflow:

1. Extracts the `GHAW-*` key from the issue body.
2. Reads the Jira issue through the Jira REST API.
3. Replaces only the workflow-managed Jira section in the GitHub body.
4. Updates the GitHub title, Priority and Effort issue fields, and mapped Project fields.
5. Preserves developer notes, checklists, links, pull requests, comments, and all content outside the managed section.
6. Removes `sync-from-jira` after requesting the updates.

Jira wins for every mapped value in this direction.

### Push GitHub into Jira

Apply `sync-to-jira` to a linked GitHub issue.

The workflow:

1. Reads the GitHub issue, organization issue fields, and Project 26 item using the configured GitHub App.
2. Calls a constrained custom safe-output job.
3. Resolves human-readable values against Jira edit metadata instead of accepting arbitrary Jira field or option IDs.
4. Updates the Jira summary, status, priority, story points, PI, source, team, requested-by value, product category, and sprint where Jira supports the requested value.
5. Posts a GitHub comment listing updated and skipped fields.
6. Removes `sync-to-jira` only after the Jira update succeeds.

GitHub wins for every mapped value in this direction. A failed Jira API operation fails the job and leaves the label present so the failure is visible.

## Field ownership and mappings

| Concept | Jira | GitHub | Direction and notes |
|---|---|---|---|
| Identity | Issue key | Key in title and body | Jira key never changes |
| Summary | Summary | Issue title after `[GHAW-*]` | Both directions |
| Status | Jira status | Project Status | Both directions through Jira transitions |
| Priority | Jira Priority | Organization Priority issue field | Both directions by matching option names |
| Size | Story Pts | Organization Effort issue field | Both directions with a lossy mapping |
| Program increment | PI | Project PI | Both directions by exact option name |
| Sprint | Sprint | Project Iteration | Both directions when an exact Jira sprint exists |
| Work origin | Source | Project Source | Both directions by exact option name |
| Team | Team | Project Team | Both directions only when Jira exposes a matching editable Team option |
| Requester | Requested by | Project Requested by | Both directions |
| Product area | Product category | Project Product category | Both directions by exact option name |
| Implementation content | Not synchronized | Developer notes, checklists, links, PRs, comments | GitHub-owned and preserved |

### Status mapping

| Jira | GitHub Project |
|---|---|
| Backlog, Open, To Do | Todo |
| In Progress, Selected for Development | In progress |
| Done, Closed, Resolved | Done |

GitHub-to-Jira status updates use an available Jira transition whose destination matches the mapped status. The workflow skips the status and reports it when no valid transition is available.

### Story points and Effort

| Jira Story Pts | GitHub Effort |
|---|---|
| 1-2 | Low |
| 3-5 | Medium |
| 8 or more | High |

The reverse mapping uses representative values:

| GitHub Effort | Jira Story Pts |
|---|---|
| Low | 2 |
| Medium | 5 |
| High | 8 |

This mapping is intentionally lossy. Pulling Jira `3` into GitHub produces `Medium`; pushing `Medium` back produces `5`.

### Jira custom fields used by this demo

The Jira `GHAW` project is team-managed. Its local field IDs are specific to this Jira project:

| Jira field | ID |
|---|---|
| PI | `customfield_10218` |
| Product category | `customfield_10219` |
| Requested by | `customfield_10220` |
| Source | `customfield_10221` |
| Story Pts | `customfield_10222` |
| Team | `customfield_10001` |
| Sprint | `customfield_10020` |

Do not copy these IDs to another Jira project. Discover that project's local fields and update both workflow source files.

## Managed and developer-owned issue content

Imported issues contain two sections:

```markdown
<!-- gh-aw-island-start:jira-sync-on-command -->
## Jira source

Jira-owned work-item facts.
<!-- gh-aw-island-end:jira-sync-on-command -->

## Developer notes

GitHub-owned implementation content.
```

`sync-from-jira` uses the gh-aw `replace-island` operation. It can replace only the content between these markers. Content outside the markers remains untouched.

`sync-to-jira` does not send the issue body, developer notes, comments, links, checklists, or pull request details to Jira.

## Authentication, permissions, model, and billing

Both agentic workflows use:

```yaml
engine: copilot
model: auto
permissions:
  contents: read
  issues: read
  copilot-requests: write
```

`copilot-requests: write` uses `${{ github.token }}` for Copilot inference and organization billing. `model: auto` lets Copilot choose an appropriate cost-conscious model.

### Jira

Repository secrets:

- `JIRA_TOKEN`: Atlassian API token
- `JIRA_EMAIL`: Atlassian account email associated with the token

The workflow sends Basic authentication only to `joshjohanning.atlassian.net`. The gh-aw network allowlist restricts Jira traffic to that host.

The Jira token needs permission to:

- Read issues and edit metadata in `GHAW`
- Edit issues
- Read and execute issue transitions
- Read board 3 sprints
- Move issues into a sprint

### GitHub Project

Repository configuration:

- Variable `PROJECT_APP_CLIENT_ID`
- Secret `PROJECT_APP_PRIVATE_KEY`

Required GitHub App access:

- Repository access to `agentic-work-item-sync-demo`
- Issues: read and write
- Organization projects: read and write

The App token reads Project values before a GitHub-to-Jira sync and writes Project values during a Jira-to-GitHub sync. GitHub App installation tokens are used because OAuth `gho_` tokens are not supported by gh-aw Project safe outputs.

### Safe write boundary

The Copilot agent runs with read-only GitHub access. It does not receive the Jira token or GitHub App private key.

- GitHub writes use gh-aw built-in safe outputs with allowlisted labels, issue fields, targets, and Project URL.
- Jira writes use the `update-jira` custom safe-output job.
- The Jira job validates the `GHAW-*` key, resolves allowed Jira options from edit metadata, and accepts named values rather than arbitrary field IDs.
- Secrets become available only in trusted post-agent jobs.

## Demo walkthrough

### Initial setup

1. Configure `JIRA_EMAIL`, `JIRA_TOKEN`, `PROJECT_APP_CLIENT_ID`, and `PROJECT_APP_PRIVATE_KEY`.
2. Install the GitHub App on this repository and grant the permissions listed above.
3. Run **Seed Jira Demo Issues** once if the `GHAW` examples do not exist.
4. Run **Configure Jira Demo Fields** to populate the source examples.
5. Run **Import New Jira Issues** to create linked GitHub issues.

### Demonstrate Jira winning

1. Edit a mapped value on `GHAW-1` in Jira, such as Requested by or Product category.
2. Add a GitHub-only note under `## Developer notes`.
3. Apply `sync-from-jira` to GitHub issue #2.
4. Confirm that the Jira source section and mapped Project field changed.
5. Confirm that the developer note remained unchanged.
6. Confirm that the command label was removed.

### Demonstrate GitHub winning

1. Edit a supported value on GitHub issue #2 or its Project item, such as the title, Priority, Effort, PI, Source, Requested by, or Product category.
2. Apply `sync-to-jira`.
3. Confirm the workflow's completion comment lists the updated Jira fields.
4. Open `GHAW-1` and confirm the values changed.
5. Confirm that the command label was removed.

### Demonstrate conflict protection

1. Apply both command labels before the workflow reads the issue.
2. Confirm that neither side is updated.
3. Confirm that the workflow posts a conflict comment and removes both labels.
4. Apply only the label representing the intended winner.

## Important limitations and watchouts

- **This is explicit synchronization, not automatic merge.** The command label chooses which side wins.
- **There is no reliable field-level last-edited timestamp.** Do not replace the directional commands with a last-write-wins rule based on item timestamps.
- **Concurrent runs are locked per issue.** The workflow locks the issue while the agent reads and decides, reducing same-item races.
- **Effort conversion is lossy.** Medium always writes `5`, even if Jira originally contained `3`.
- **Options require exact names.** PI, Source, Team, Product category, Priority, Iteration, and Sprint names must align.
- **Sprint synchronization depends on board 3.** GitHub Iteration is pushed only when an exact active or future Jira sprint exists.
- **Team-managed Jira fields are project-local.** Field IDs and editability differ between Jira projects.
- **Jira transitions constrain Status.** The desired destination must be available from the issue's current state.
- **Skipped fields are visible.** The GitHub-to-Jira completion comment lists fields Jira could not update.
- **Partial Jira updates are possible.** Jira field updates, transitions, and sprint assignment are separate API operations. A later failure cannot automatically roll back an earlier successful operation.
- **The scheduled importer is Jira-to-GitHub only.** It never pushes GitHub changes to Jira.
- **Only the `GHAW` project is allowed.** The Jira write job rejects keys outside `GHAW-*`.
- **The demo does not sync attachments, comments, relationships, assignees, labels, or rich-text descriptions bidirectionally.**
- **The demo is public.** Do not add customer-sensitive or confidential work-item content.

For production use, add a persistent per-field baseline and idempotency ledger. That would allow automatic one-sided changes, field-by-field merges, and explicit conflict records without relying on timestamps.

## Local authoring and validation

Install and use the gh-aw CLI:

```bash
gh extension install github/gh-aw
gh aw compile jira-import-new jira-sync-on-command
gh aw validate jira-import-new jira-sync-on-command
```

Useful operational commands:

```bash
gh aw status
gh aw logs jira-sync-on-command
gh aw audit <run-id-or-url>
```

The repository is initialized for agentic authoring, so Copilot can create, compile, validate, and debug these workflows.
